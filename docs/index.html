What it is

Simple, trust-based ride-sharing

Telekocsi solves a narrow, everyday problem: getting a small group of people from A to B without the overhead of a full ride-hailing platform. Anyone with a registered vehicle can list a ride; anyone else can book a seat on it instantly. Payment happens off-platform, in cash — the app's job is matching people and getting contact details into the right hands the moment a booking is confirmed.

Features

What you can do in the app

A walkthrough of the core flows, from the perspective of a driver or a passenger.

Accounts & verification

Sign up with a username, email and phone number, confirm your email through a verification link, and log in with either your username or email.

Vehicle management

Add one or more vehicles to your account. A vehicle can be freely edited or removed — until it's tied to an active listing, at which point it's locked to protect passengers who already booked.

Ride listings

Create a listing for a specific trip: route, date, price per seat and the vehicle to use. Seat count defaults to the vehicle's capacity and can be adjusted before anyone books.

Search & filtering

Browse upcoming rides sorted by departure time, and filter by origin, destination, date range or minimum available seats.

Instant booking

No approval step — a seat is booked the moment you request it, as long as capacity allows. Booking again on the same listing merges into your existing booking instead of creating a duplicate.

Automatic contact sharing

Once a booking is confirmed, both sides automatically receive each other's phone number and email by mail — and the passenger sees the vehicle's license plate.

Cancellations, done carefully

Every irreversible action — cancelling a booking, deleting a listing — asks for confirmation first. A driver-cancelled listing marks affected bookings as "Removed", clearly distinct from a passenger's own "Cancelled".

Unified activity lists

"My Bookings", "My Listings" and "My Passengers" all follow the same pattern: an upcoming block sorted soonest-first, and a combined past block below it — no separate tabs to hunt through.

Under the hood

Tech stack

A small, modern stack chosen to keep the app fast to build and cheap to run.

Frontend

  • React 19Component-driven UI, function components with hooks
  • TypeScriptTyped data models shared across pages and API calls
  • ViteDev server and production bundler
  • Tailwind CSS v4Utility-first styling, no separate design-token layer

Backend

  • SupabaseHosted Postgres, auth and instant REST/RPC access
  • PostgreSQLSchema, views and business logic close to the data
  • Row-Level SecurityAccess rules enforced at the database layer
  • RPC functionsServer-side logic for booking, cancellation and locking rules
How it was built

Development process

Telekocsi wasn't built from a fixed spec handed down once — it grew through repeated rounds of feedback, each one traceable from requirement to ticket to code.

1

Starting scaffold

The frontend began as a design exported from Figma Make, giving the project a working React/Vite/Tailwind base and a set of UI screens to build real functionality behind.

2

Requirements analysis

A structured requirements interview turned the initial idea into a formal system-analysis specification: data model, main process flow and numbered business rules — the single source of truth for how the app should behave.

3

Iterative feedback rounds

As real usage surfaced gaps and edge cases, feedback was batched into versioned rounds (currently at v7). Each round adds or amends numbered rules in the specification and is broken down into a matching set of backlog tickets.

4

Tracked backlog

Every feature and fix lives as a ticket with user-story wording and Given/When/Then acceptance criteria, cross-referenced back to the specification's rule numbers — so any change is traceable in both directions.

5

Implementation & verification

Changes land as database migrations (schema, Row-Level Security, RPC functions) alongside the React frontend, checked with strict type-checking and a production build before being considered done.

The loop, in short: feedback comes in → the specification is updated → backlog tickets are created or amended → the database and frontend are implemented → the change is verified end-to-end. Development was carried out with AI-assisted, agentic tooling throughout, which is what made keeping specification, backlog and code in sync across seven iterations practical rather than a maintenance burden.
What's next

Roadmap

Deliberately out of scope for the current version, but planned for a later phase.
